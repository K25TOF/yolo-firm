## Q1: Skip Rate — 529/784 Ticker-Date Pairs Skipped

The engine skips a ticker-date pair when there are insufficient bars to reach `min_stabilization_bars` before any RTH signal can fire. Based on my memory note from LC-2025-003:

> *min_stabilization_bars must be >= 20*

The HYP-025 config should have been run with `min_stabilization_bars = 20`. If it was run with a lower value — or if the default was used — some pairs would have been evaluated on noisy early bars and produced garbage signals. But that would *increase* trades, not explain skips.

**Likely skip causes (engine mechanics):**

1. **Insufficient bar count.** If a ticker-date pair has fewer bars than `min_stabilization_bars`, the engine skips it entirely. Sub-$1 stocks with thin pre-market data sometimes have truncated RTH bar files — fewer than 20 bars cached.

2. **Missing cache file.** If the 1-min bar file for a ticker-date doesn't exist in `analysis/cache/`, the engine skips that pair silently. With ~98k bar files across ~5,000 tickers × 180 days, not every combination exists. The 49-ticker dataset used in EXP-023 was hand-curated — if HYP-025 ran against a broader set (e.g., all scanner-flagged tickers across 17 days), many pairs would have no cached data.

3. **RTH bar count below threshold.** Even if a file exists, if the ticker opened late or had a trading halt, RTH bars may be <20.

**Key question I cannot answer from memory:** What was the *total universe* fed into HYP-025? If it was the full scanner-flagged set (~30 tickers/day × 17 days = ~510 pairs), many of those tickers won't have cached bars. If it was the 49-ticker EXP-023 universe (49 × 17 = 833 pairs — close to 784), the skip rate of 67% is suspicious and suggests missing cache files or bar count issues.

## Q2: Trade Count Anomaly — 653 vs ~85 for vol_filter

This is the more important issue. Three candidate explanations:

**Candidate A: `less_than` operator on `ema_gap_acceleration` is not filtering — it's firing continuously.**

`ema_gap_acceleration` measures `ema_gap[i] - ema_gap[i - lookback]`. For a grinder stock in a slow steady climb, this value oscillates around 0 — sometimes +0.3, sometimes -0.2. The `less_than 1.0` condition is TRUE almost continuously during normal price action, not just at entry signals.

The intended logic was: *"only enter when momentum is not accelerating."* But `less_than 1.0` is a static threshold check evaluated on every bar. If `ema_gap_acceleration` is routinely below 1.0 during consolidation periods — which it will be — it contributes almost nothing to filtering. It only blocks entries when acceleration is >= 1.0, which is rare outside of genuine spike moments.

**This is likely the primary cause of 653 trades.** The acceleration filter is an AND condition with `ema_gap crosses_above 1.0`. But `ema_gap crosses_above 1.0` fires far more frequently than `crosses_above 3.0` — many more crossings per day per ticker. And `ema_gap_acceleration < 1.0` barely reduces that count.

**Candidate B: `ema_gap crosses_above 1.0` is a much lower bar than `crosses_above 3.0`.**

vol_filter requires `ema_gap crosses_above 3.0`. HYP-025 requires `crosses_above 1.0`. The gap between EMA3 and EMA9 exceeds 1.0% far more often than 3.0% — any minor price uptick can cause this crossing. 653 trades vs 85 is roughly a 7.7x multiplier, which is directionally consistent with the lower threshold generating many more crossings per day.

**Candidate C: `vwap_distance >= 2%` is also weak as a filter.**

As noted in my memory: VWAP is noisy on sub-$1 stocks (bid-ask 1-5%, single blocks shift VWAP 0.5-2%). Most RTH entries on momentum stocks are above VWAP by 2%+ anyway — this threshold is rarely a binding constraint.
