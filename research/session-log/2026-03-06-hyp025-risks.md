## Risk #1: Data Snooping / In-Sample Overfitting (SEVERITY: HIGH)

**The Specific Threat:**

EXP-021 found patterns in 60 trades across Feb 24–Mar 3. Three of those findings became entry rules:

1. **Gap acceleration < 1.0%** — derived from EXP-021 Fig: "Accelerating gap (>1%) = -54.9% PnL" (24 trades). This threshold is *reverse-engineered from the outcome distribution*, not from forward theory. On the 6-day Feb 24–Mar 3 subset, this rule will perform exactly as observed. On Feb 10–23, its performance is untested.

2. **VWAP >= 2% distance** — EXP-021 showed "winners further above VWAP" (14.7% vs 12.4%), but the gap was marginal. The 2% rule is not derived from EXP-021 statistics; it's been added as a design choice. However, *the principle* (VWAP filtering helps) was observed in the same dataset.

3. **EMA gap 1.0% threshold** — This is not derived from EXP-021. It's borrowed from IDEA-016 conceptual definition ("grinders: 1–3% EMA gap"). But there's no data in EXP-021 that validates 1.0% vs 0.8% vs 1.2%.

**When we run HYP-025 backtest on the full 17-day dataset:**
- Days Feb 24–27, Mar 2–3 will show inflated results because we've optimised the gap_acceleration rule on those exact trades.
- Days Feb 10–23 (11 days, untested) are the only truly out-of-sample data.
- If Feb 10–23 produce < 40% WR, the hypothesis fails. If they produce >= 40%, we can't distinguish between (a) the rule is genuinely good, or (b) we got lucky on two subsets.

**Isolation test needed:**
Report per-day WR for Feb 10–23 separately from Feb 24–Mar 3. If Feb 10–23 WR < Feb 24–Mar 3 WR by >10pp, the hypothesis is suspect.

## Risk #2: Sample Size on Slow_Grind Universe Is Inadequate (SEVERITY: HIGH)

**The Specific Threat:**

EXP-019 identified 7 slow_grind tickers per day. Over 17 days, that's ~119 potential grind setups. But:

- Not all 7 appear every day (some are one-day phenomena)
- The grind rule is *selective* — it will enter on fewer signals than vol_filter (requires 1.0% EMA gap + VWAP + non-accel)
- Expected trade count on grinders: 15–30 trades across 17 days (rough guess)

**The problem:**
- HYP-025 success criterion is "win rate >= 40%"
- With 20 trades, a 40% WR = 8 wins, 12 losses
- Confidence interval (binomial, 95%) around 40% with n=20: ±13.8pp → range 26%–54%
- With 20 trades, we can't distinguish between "strategy works at 40%" and "lucky sample"

**Guiding principle #6 applies here:** "Don't rely on outlier runners." With only 20–30 trades:
- One big winner (MOBX +40%) inflates WR by 5pp
- One big loser (like Feb 12's -32%) deflates WR by 5–10pp
- We need 50+ trades minimum to have confidence outliers aren't driving the result

**Recommendation:**
- If final trade count on grinder rules is < 40 trades, report results as "directional, not validated"
- Report top 3 trades by PnL and bottom 3 — if there's a single +20% trade or -10% loss, flag it explicitly

## Risk #3: EMA Gap Acceleration Is a High-Latency Derived Indicator (SEVERITY: MEDIUM)

**The Specific Threat:**

The entry rule "ema_gap_acceleration_3b < 1.0%" requires computing ROC (rate of change) of EMA gap over 3 bars:
```
gap_accel = (gap[bar_i] - gap[bar_i-3]) / gap[bar_i-3]
```

In the backtester:
- Bars 0–2: insufficient history, can't compute accel (dropped or NaN)
- Bar 3 onward: accel value is final (no data leakage so far)

**But the real issue is evaluation timing:**

When we check the entry condition at bar N's close, we have:
- `gap[N]` — current EMA gap (final for bar N)
- `gap[N-1]`, `gap[N-2]`, `gap[N-3]` — prior bars' gaps (all final)
- `accel = (gap[N] - gap[N-3]) / gap[N-3]` — fully determinable

This is **clean** — no forward-looking data.

**However, the *concept* of "non-accelerating gap" was identified in EXP-021 by looking at the entire *post-trade history* of winners vs losers:**
- EXP-021 computed gap_accel on each trade's entry bar and compared distributions
- Losers had median gap_accel +3.08%, winners +3.00% — almost identical!
- Then EXP-021 bucketed by accel thresholds: "accelerating (>1%) = -54.9% PnL"

**This bucketing is a form of look-ahead:** We observed trade outcomes, then looked backward to find entry conditions that separated them. The threshold of 1.0% was chosen because trades > 1.0% accel had poor outcomes. On a different dataset, this threshold might be 0.8% or 1.5%.

**The leak is subtle:**
- We're not leaking bar-by-bar prices or fill prices
- But we're *fitting the threshold (1.0%) to the observed distribution of outcomes*
- On the exact same dataset, the fit will hold. On new data, it may not.

**Mitigation:**
- Run HYP-025 on a date range *outside* Feb 10–Mar 4 (e.g., Mar 5–20 or Feb 1–9) as a true out-of-sample test
- If results are significant, the rule is genuine
- If results are weak or contradictory, the 1.0% threshold was overfit

## Look-Ahead Bias Assessment: Bar-Close Evaluation Timing

I'll trace through the engine's entry evaluation at each bar to identify any data leakage.

### The Engine's Entry Check (per `engine.py` logic)

At each bar close (N), the engine:

1. **Update all indicators** — EMA, volume_ratio_ema, VWAP, ATR, ema_gap_acceleration
2. **Evaluate entry conditions** (in order):
   ```
   if ema_gap crosses_above 1.0% AND
      volume_ratio_ema >= 2.0 AND
      price >= vwap × 1.02 AND
      ema_gap_acceleration < 1.0%:
       enter at bar N close
   ```
3. **If all true:** entry price = bar N's close price

### Data Leakage Check: Each Rule

| Rule | Data Available at Bar N Close | Leakage? | Notes |
|------|-----|---|---|
| `ema_gap crosses_above 1.0%` | `gap[N-1]`, `gap[N]` (both final) | **No** | Crossing logic requires prior bar; both bars closed |
| `volume_ratio_ema >= 2.0` | `vol[N]`, EMA(20 bars) all closed | **No** | Current volume finalized at N close |
| `price >= vwap × 1.02` | `vwap[N]`, `close[N]` | **No** | Session VWAP computed on closed bars 0–N |
| `ema_gap_acceleration < 1.0%` | `gap[N]`, `gap[N-1]`, `gap[N-2]`, `gap[N-3]` | **No** | All 4 bars closed; ROC is deterministic |

**Verdict on look-ahead:** ✅ **Clean.** No forward-looking data used. All rules evaluate only closed bars.

### Risk #2 (NEW): VWAP >= 1.02 Is Untested on Sub-$1 Stocks

**The Specific Threat:**

HYP-024 (VWAP distance validation) tested on 49 tickers and found:
- VWAP >= 5% gave +4.2pp WR (34% → 38%)
- VWAP >= 10% gave best results
- **Result: INCONCLUSIVE** — didn't meet +5pp bar

HYP-025 Phase 1 now uses **VWAP >= 1.02 (2% distance)** — a tighter rule than what HYP-024 tested.

**Why this matters for sub-$1 stocks:**

On MOBX ($0.46 open), a 2% VWAP distance is $0.009. At the bid-ask spread (1-5% on micro-caps), this is noise.

- Backtester uses the consolidated close price from Polygon, which is a synthetic NBBO
- In live trading, our fill price might be 3% worse due to slippage
- The "price >= VWAP × 1.02" condition might be true on paper but false in reality

**Dataset composition risk:**
- 49 tickers includes MOBX, DXST, other sub-$1 runners
- These are the highest-PnL tickers (MOBX alone drives +47% returns)
- If the 2% VWAP rule breaks on sub-$1 entries, the hypothesis collapses on its best profit sources

**Backtester doesn't model slippage.** We're assuming entry fills exactly at bar close. On sub-$1 stocks with 2% bid-ask, this is heroic.

**Mitigation:** After HYP-025 backtest, isolate results by price bucket:
- Sub-$1 tickers only (MOBX, DXST, RYDE, INEO, etc.)
- $1–5 tickers (NCI, STAK, CCHH, etc.)
- $5+ tickers

If sub-$1 WR >= 40% but $1–5 WR < 35%, the VWAP rule is working by accident (noise-induced), not logic.

**Effort:** 5 min (post-backtest grouping)

### Risk #3 (NEW): Stabilization Bars Inadequate for EMA Gap Acceleration

**The Specific Threat:**

The backtester requires `min_stabilization_bars` before any trade can fire. For vol_filter_ema10, this is set to 10.

HYP-025 Phase 1 adds a new indicator: `ema_gap_acceleration` (3-bar ROC).

To compute accel cleanly, we need:
- `ema_gap[N]`, `ema_gap[N-1]`, `ema_gap[N-2]`, `ema_gap[N-3]` all valid
- EMA(3,9) on bars 0–3 to produce valid gap values

The engine stabilizes EMA after 20 bars (default `max(3, 9) + 11`). So:
- Bar 0–19: EMA stabilizing, gap values may be inflated/deflated
- Bar 20+: EMA stabilized, gap values trustworthy
- Bar 23+: gap_accel has 4 clean bars and is trustworthy

**Is min_stabilization_bars = 10 enough?** 

For EMA(3,9) stabilization, no. The 3/9 pair needs ~20 bars to produce stable gap values. With min_stab = 10:
- Bars 10–19: accel is being computed on not-yet-stable EMAs
- These early entries will have artificially high or low accel values
- The "gap_accel < 1.0%" rule will trigger on noise

**Dataset impact:**
- On fast-moving tickers (MOBX, DXST, RYDE), signals fire within the first 50 bars of RTH
- Many first entries for grinders will occur on bars 10–23 when accel is still noisy
- The rule will appear to work on the in-sample data (Feb 24–Mar 3, which set the 1.0% threshold) but fail on new data

**Backtester config check:** What is `min_stabilization_bars` set to in the HYP-025 Phase 1 spec?

(Looking at the spec from Manager's context... Phase 1 doesn't specify. Likely defaulting to 10 or 20 depending on engine default.)

**Mitigation:** 
- Confirm min_stabilization_bars = max(20, period of slowest indicator in rule)
- For HYP-025: min_stab should be 20 (to stabilize EMA 3/9)
- Re-run backtest if current setting is < 20
